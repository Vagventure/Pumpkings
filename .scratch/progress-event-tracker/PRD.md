# Progress Event Tracker PRD

## Problem Statement

The game currently triggers event and reward flow from awareness tiers only. This makes milestone events too narrow: designers cannot trigger narrative or reward events from total gold gathered or total threat produced, even though those are core parts of the gameplay loop.

The current tier model also mixes three concerns under one awareness-specific name: threshold tracking, event presentation, and reward choice. As more milestone sources are added, `TierDefinition` and tier numbers become misleading. The game needs one progress event model that can be reused for awareness, gold gathered, and threat produced.

## Solution

Replace awareness-specific tiers with unified progress events. A new runtime `ProgressTracker` will count total awareness, total gold gathered, and total threat produced during the current run. `LevelController` will expose three designer-configurable progress event lists: awareness events, gold gathered events, and threat produced events.

When any total crosses a configured threshold, `ProgressTracker` will publish the matching progress event. `RewardManager` will own one FIFO queue for all progress events, so event popups and reward choices never overlap. Progress events may show a narrative event, offer rewards, do both, or do neither if intentionally empty.

## User Stories

1. As a designer, I want to configure awareness milestones, so that awareness purchases can trigger story or reward moments.
2. As a designer, I want to configure gold gathered milestones, so that collecting enough lifetime gold can trigger events even after the player spends gold.
3. As a designer, I want to configure threat produced milestones, so that the level can react to the total amount of threat generated over the run.
4. As a designer, I want progress events to use thresholds instead of tier numbers, so that each metric can have its own pacing curve.
5. As a designer, I want progress event lists sorted by threshold, so that event order is predictable in the Inspector and at runtime.
6. As a designer, I want progress event rewards to be optional, so that some events can be purely narrative.
7. As a designer, I want progress event prefabs to be optional, so that some milestones can go straight to reward choice.
8. As a designer, I want awareness, gold, and threat events to share the same definition shape, so that adding events does not require learning three systems.
9. As a player, I want milestone events to appear when I reach meaningful run totals, so that progress feels recognized.
10. As a player, I want gold milestones to care about total gold earned, so that spending gold does not erase milestone progress.
11. As a player, I want threat milestones to reflect the total pressure generated by the level, so that events can react to escalation over time.
12. As a player, I want only one event flow at a time, so that popups and reward choices do not stack or conflict.
13. As a player, I want rewards to appear after a milestone event when configured, so that milestone moments can still unlock bonuses.
14. As a player, I want gameplay to resume cleanly after an event-only milestone, so that narrative events do not block the run.
15. As a programmer, I want scoring systems to publish facts rather than own milestone rules, so that scoring remains focused on current pollution, budget, and purchase validation.
16. As a programmer, I want a dedicated progress tracker, so that total progress and threshold detection are isolated in one module.
17. As a programmer, I want `RewardManager` to consume progress events without caring which metric produced them, so that event presentation remains centralized.
18. As a programmer, I want old awareness tier terminology removed from this flow, so that code vocabulary matches the generalized model.
19. As a programmer, I want runtime totals to reset with the scene/run, so that no persistence system is introduced for this short browser game.
20. As a programmer, I want total threat to be based on post-bonus pollution values, so that threat milestones match the actual pressure added to current pollution.
21. As a programmer, I want total gold gathered to be based on post-bonus trash income, so that gold milestones match actual earned gold.
22. As a programmer, I want empty or exhausted reward lists to avoid blocking the queue, so that a misconfigured reward set cannot stall future events.
23. As a programmer, I want progress bars to use the next awareness threshold as their target, so that awareness UI continues to work after tier removal.
24. As a programmer, I want static events to connect existing managers, so that this change follows the current project communication style.

## Implementation Decisions

- Replace `TierDefinition` with a unified `ProgressEventDefinition`.
- `ProgressEventDefinition` contains `requiredValue`, `eventPrefab`, `eventDefinition`, `choicesToShow`, and `rewards`.
- Remove tier number semantics from the progress event flow. Thresholds are the source of truth.
- `LevelController` owns three lists: awareness events, gold gathered events, and threat produced events.
- `LevelController` validates each progress event and sorts lists by `requiredValue`.
- Add `ProgressMetric` with awareness, gold gathered, and threat produced values.
- Add a runtime `ProgressTracker` singleton.
- `ProgressTracker` owns `TotalAwareness`, `TotalGoldGathered`, and `TotalThreatProduced`.
- Runtime totals reset with the scene/run. No save file, PlayerPrefs, or cross-session persistence is included.
- `ProgressTracker` tracks the next event index per metric after sorting.
- `AwarenessManager` no longer owns threshold detection or highest reached tier state.
- `AwarenessManager` still owns awareness value updates and awareness bar updates.
- `AwarenessManager` publishes an awareness gained event when awareness increases.
- `ScoringService` publishes a gold gathered event when trash removal grants gold.
- `ScoringService` publishes a threat produced event when trash spawn adds pollution/threat.
- Gold gathered uses gross lifetime gold earned from trash, not current budget.
- Threat produced uses the final post-bonus pollution value that was actually added to current pollution.
- `RewardManager` subscribes to progress events and enqueues them in one FIFO queue.
- `RewardManager` continues to own pausing, event prefab instantiation, event completion, reward choice, and resume behavior.
- A progress event with an event prefab and no rewards shows the event and then continues.
- A progress event with rewards and no event prefab opens reward choice immediately.
- A progress event with neither event prefab nor rewards should be skipped with a warning.
- If configured rewards are unavailable because they are already active or gated, the event should still show; reward choice is skipped and the queue advances.
- Static events remain the primary cross-manager communication style, matching the current codebase.
- Existing event prefab handling through `EventController` and `EventDefinition` should be reused.

## Testing Decisions

- Test external behavior, not private implementation details. Tests should verify totals, threshold publication, queue ordering, and reward/event flow outcomes.
- The best isolated module to test is `ProgressTracker`, because it has a simple interface and contains the threshold crossing rules.
- `ProgressTracker` tests should cover awareness, gold gathered, and threat produced totals.
- `ProgressTracker` tests should cover crossing multiple thresholds in one increment.
- `ProgressTracker` tests should cover independent next-event indexes per metric.
- `ProgressTracker` tests should cover sorted threshold behavior.
- `ScoringService` tests should verify that post-bonus trash income is published as gathered gold when trash is removed.
- `ScoringService` tests should verify that post-bonus trash pollution is published as produced threat when trash is added.
- `AwarenessManager` tests should verify that awareness gains are published without performing milestone checks locally.
- `RewardManager` tests should verify FIFO ordering across mixed metrics.
- `RewardManager` tests should verify event-only, reward-only, event-plus-reward, and empty-event behavior.
- If Unity play mode tests are too heavy for this project right now, start with focused edit mode tests around plain threshold logic and use manual scene verification for UI/prefab wiring.

## Out of Scope

- Per-trash-type threat totals are out of scope.
- Cross-session or cross-run persistence is out of scope.
- A separate save/load system is out of scope.
- New event UI design is out of scope.
- New reward types are out of scope.
- Rebalancing the actual threshold values is out of scope.
- Changing lose conditions or current pollution behavior is out of scope.
- Changing budget spending rules is out of scope.
- Replacing static events with dependency injection or a broader event bus is out of scope.

## Further Notes

- The existing `TierDefinition` data in Unity may need to be recreated or checked manually after the class is unified into `ProgressEventDefinition`.
- The feature should preserve current awareness event behavior from the player perspective, except that the underlying vocabulary becomes progress-event based.
- The final coding task should include a Unity setup section because `LevelController` and the new `ProgressTracker` require scene/Inspector verification.
